= Java Learning Project - Chapter Overview

== Structure

The project is organized as a sequence of small learning packages.

For regular learning chapters:

* `Main.java` provides an executable entry point;
* `README.adoc` contains the core theory required for that chapter;
* `EXERCISES.adoc` uses only the core README and the Java examples from the same chapter;
* additional Java files provide focused examples;
* some chapters contain `DEEP_DIVE.adoc` for connected concepts that need more detail but are not required for the chapter exercises.

`_00_glossary` is intentionally different.
It is a reference and entry area, so it contains no executable `Main.java` and no exercises.
Its cheat sheet links to glossary definitions, and glossary definitions link to the chapter in which a concept is explained or demonstrated.

The numbered package names such as `_01_...` are a deliberate teaching convention that keeps the lesson order visible in the IDE.
They are not presented as a normal production-package naming style.

== Core vs Deep Dive

The documentation has two levels when a chapter needs them:

README.adoc::
The required chapter material. Exercises may assume this content.

DEEP_DIVE.adoc::
Additional or more complex explanations connected to glossary terms. Exercises in that chapter do not require this material unless the course is deliberately extended.

This structure keeps chapter READMEs readable while still giving glossary links a meaningful path to a detailed explanation and code example.

== Teaching Order

|===
|Package |Topic

|`_00_glossary`
|Reference vocabulary and cheat sheets

|`_01_naming_conventions`
|Naming conventions and meaningful names

|Comments, Javadoc, TODO/FIXME, and documentation choices

|`_03_datatypes`
|Primitive/reference types, variables, conversions, and wrapper classes

|`_04_classes_objects`

|`_08_delegation_inheritance`

|Runtime polymorphism, overriding, and dynamic dispatch

|`_90_generics`
|Optional later chapter on generic types, collections, and generic methods
|===

== Commenting Principle

A concept is explained in code comments when it is first introduced.
Later chapters assume that concept is known.

Other comments are used only when they answer one of these questions:

* Why is this done?
* What does this example demonstrate?
* What should a learner pay attention to?

The goal is for later code to look increasingly like normal production code while the theory builds progressively.
