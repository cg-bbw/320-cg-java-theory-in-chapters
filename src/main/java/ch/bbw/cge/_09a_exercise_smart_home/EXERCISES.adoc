= Smart Home Exercise – Lösungen

== Part 1: Inspect the Existing Code

. Welche Klasse ist abstrakt?
+
`Device` ist abstrakt und kann nicht direkt instanziiert werden.

. Welche Klassen erben von einer anderen Klasse?
+
`Lamp` und `Thermostat` erben von `Device`.
In der optionalen Erweiterung erbt auch `SmartPlug` von `Device`.

. Welche Klasse implementiert Switchable?
+
`Lamp` implementiert `Switchable`.
In der optionalen Erweiterung implementiert auch `SmartPlug` dieses Interface.

. Welche Klasse speichert mehrere Device-Referenzen?
+
`Room` speichert sie in `List<Device> devices`.

. Welche Klasse speichert mehrere Room-Referenzen?
+
`SmartHome` speichert sie in `List<Room> rooms`.

. Wo erkennt man Komposition?
+
Zwischen `SmartHome` und `Room`.
Das SmartHome erstellt seine Räume selbst in `addRoom(...)`
und verwaltet sie als eigene Bestandteile.

. Wo erkennt man Aggregation?
+
Zwischen `Room` und `Device`.
Die Geräte werden unabhängig erstellt und anschliessend einem Raum hinzugefügt.

. Welche Beziehungen sind unidirektional?
+
`SmartHome` kennt seine Räume, aber Room besitzt keine Rückreferenz
auf SmartHome.
+
`Room` kennt seine Geräte, aber Device besitzt keine Rückreferenz auf Room.
+
Auch die Nutzung von Switchable durch den Controller erfolgt nur
in eine Richtung. Die Geräte kennen den Controller nicht.

== Part 2: Complete Room

Die Methode speichert die übergebene Gerätereferenz:

[source,text]
----
public void addDevice(Device device) {
    devices.add(device);
}
----

Dies unterstützt Aggregation, weil das Gerät bereits unabhängig
vom Raum existiert. Der Raum erstellt das Gerät nicht selbst.

== Part 3: Complete SmartHome

[source,text]
----
public Room addRoom(String name) {
    Room room = new Room(name);
    rooms.add(room);
    return room;
}
----

Das SmartHome erstellt und verwaltet seine Räume.
Deshalb wird die Beziehung im vorgesehenen Modell als Komposition verstanden.

Java erzwingt dieses Besitzverhältnis nicht automatisch.
Der öffentliche Room-Konstruktor erlaubt technisch auch,
Räume ausserhalb eines SmartHome zu erstellen.

== Part 4: Complete the Device Classes

=== Bestandteile von Device

* Gemeinsames Feld: `private final String name`.
* Konstruktor: `public Device(String name)`.
* Konkrete Methode: `public String getName()`.
* Abstrakte Methode: `public abstract String getStatus()`.

=== Lamp

* `turnOn()` setzt `switchedOn` auf `true`.
* `turnOff()` setzt `switchedOn` auf `false`.
* `getStatus()` liefert den Gerätenamen und `ON` oder `OFF`.
* Das boolean-Instanzfeld hat anfangs den Standardwert `false`.

=== Thermostat

`getStatus()` liefert den Gerätenamen und die Temperatur in Grad Celsius.

=== Antworten

. Warum gehört name in Device?
+
Alle Geräte besitzen einen Namen.
Das gemeinsame Feld und die Methode `getName()` müssen dadurch
nicht in jeder Geräteklasse erneut geschrieben werden.

. Warum ist getStatus() abstrakt?
+
Jedes konkrete Gerät muss einen Status liefern,
aber der Inhalt hängt vom Gerätetyp ab.
Eine Lampe meldet ihren Schaltzustand, ein Thermostat seine Temperatur.

. Warum implementiert Lamp Switchable, Thermostat aber nicht?
+
Die Lampe kann in diesem Modell ein- und ausgeschaltet werden.
Der Thermostat verwaltet hier nur seine Temperatur.
Er bietet in diesem vereinfachten Modell keine Schaltfunktionen an.

== Part 5: Complete the Controller

[source,text]
----
public void switchOn(Switchable device) {
    device.turnOn();
}

public void switchOff(Switchable device) {
    device.turnOff();
}
----

=== Welches Objekt verändert seinen Zustand?

Das übergebene Gerät selbst, beispielsweise die Lampe.
Seine Methode verändert das Feld `switchedOn`.

=== Warum ist das Delegation?

Der Controller führt die Zustandsänderung nicht selbst durch.
Er ruft die passende Methode am übergebenen Gerät auf
und übergibt diesem damit die Aufgabe.

== Part 6: Complete Main

Main erstellt:

* das SmartHome „My Smart Home“;
* die Räume „Living Room“ und „Office“ über `home.addRoom(...)`;
* die Ceiling Lamp und den Living Room Thermostat mit 21.5 °C;
* die Desk Lamp und den Office Thermostat mit 20.0 °C.

Die Geräte werden ihren Räumen hinzugefügt.

Der Controller schaltet die Ceiling Lamp ein.
Die Desk Lamp wird zum Prüfen kurz ein- und wieder ausgeschaltet.
Bei der Ausgabe ist sie ausgeschaltet.

Eine äussere Schleife durchläuft die Räume.
Eine innere Schleife durchläuft die Geräte des jeweiligen Raumes
und gibt deren Status aus.

== Part 7: Review the Relationships

[cols="2,2,2,3", options="header"]
|===
|Relationship |Type |Direction |Multiplicity

|SmartHome – Room
|Komposition
|SmartHome → Room
|Vorgesehenes Modell: ein SmartHome hat 1..* Räume;
jeder zugehörige Raum gehört zu einem SmartHome.

|Room – Device
|Aggregation
|Room → Device
|Ein Raum enthält 0..* Geräte.
Im Code kann dasselbe Gerät in 0..* Räumen gespeichert werden.

|Lamp – Device
|Vererbung / Generalisierung
|Lamp → Device
|Keine Assoziationsmultiplizität; Lamp ist ein Untertyp von Device.

|Lamp – Switchable
|Interface-Realisierung
|Lamp → Switchable
|Keine Assoziationsmultiplizität; Lamp erfüllt den Switchable-Vertrag.

|SmartHomeController – Switchable
|Abhängigkeit durch Nutzung; Delegation
|SmartHomeController → Switchable
|Keine dauerhaft gespeicherte Beziehung;
pro Methodenaufruf wird ein Switchable-Objekt übergeben.
|===

=== Modell und tatsächlicher Code

Die Aufgabe sieht für SmartHome zu Room die Multiplizität `1..*` vor.
Direkt nach `new SmartHome(...)` ist die Liste jedoch noch leer.
Der Code erlaubt deshalb zunächst `0..*` Räume.
Main stellt den vorgesehenen Zustand durch das Hinzufügen zweier Räume her.

Der Code verhindert nicht, dass dieselbe Gerätereferenz
mehreren Räumen hinzugefügt wird.
Eine Beschränkung auf genau einen Raum wäre eine zusätzliche Regel,
die hier nicht implementiert ist.

== Optional Extension: SmartPlug

`SmartPlug` erbt von Device und implementiert Switchable.

Die Klasse besitzt einen eigenen Schaltzustand.
Sie implementiert `turnOn()`, `turnOff()` und `getStatus()`.

Der vorhandene Controller kann die Steckdose unverändert steuern,
weil seine Methoden den Typ Switchable erwarten.
Er muss die konkrete Geräteklasse nicht kennen.

=== Begriffe am Beispiel

* Aggregation: Room speichert unabhängig erstellte Geräte.
* Komposition: SmartHome erstellt und verwaltet seine Räume.
* Vererbung: Lamp, Thermostat und SmartPlug erweitern Device.
* Abstrakte Klasse: Device definiert gemeinsame Eigenschaften und Verhalten.
* Interface: Switchable legt die Schaltoperationen fest.
* Überschreiben: Die Geräte implementieren `getStatus()` mit `@Override`.
* Delegation: Der Controller ruft `turnOn()` oder `turnOff()` am Gerät auf.
