= Object Relationships

== Learning Goals

After this chapter, you should be able to:

* recognize a has-a relationship in Java code;
* explain association as a general relationship between objects;
* distinguish aggregation and composition as modeling concepts;
* identify relationship direction;
* read simple UML multiplicities.

== Key Terms

Association::
Association is the broadest relationship term in this chapter. It describes that objects know about or interact with each other. A has-a relationship is a structural form of association in which one object stores another object as part of its state. Aggregation and composition add more specific whole-part semantics to such a relationship.

Has-a relationship::
A has-a relationship describes that one object contains or owns another object as part of its structure. In Java, this is commonly represented by a field that refers to another object. Aggregation and composition are more specific forms of has-a relationships that describe different kinds of whole-part relationships.

Aggregation::
A whole-part relationship in which the part can conceptually exist independently of the whole.

Composition::
A stronger whole-part relationship in which the whole conceptually owns the part and controls its lifetime in the model.

Unidirectional relationship::
Only one side stores or uses a reference to the other side.

Multiplicity::
The number of objects that may participate at one end of a relationship.

== Important: Relationships Describe the Model

Java has no `aggregation` or `composition` keyword.
The difference is determined by the intended ownership and lifetime of the objects in the model.

A field alone does not prove whether a relationship should be called aggregation or composition.

== Composition Example

`Car` creates its own `Engine`:

[source,java]
----
public Car(String model) {
    this.model = model;
    this.engine = new Engine();
}
----

In this model, the `Engine` is owned by the `Car` and is created as part of it.

Composition is therefore a strong form of has-a relationship in which the whole conceptually controls the lifetime of the part.

Simplified UML:

[source,text]
----
Car ◆──────── Engine
----

The filled diamond is placed at the `Car` side because `Car` represents the whole.

== Aggregation Example

A `Player` can exist independently of a `Team`.

The players are created first:

[source,java]
----
Player firstPlayer = new Player("Sam");
Player secondPlayer = new Player("Lee");
----

A team can then be created and the existing players can be added to it:

[source,java]
----
Team team = new Team("Blue Team");

team.addPlayer(firstPlayer);
team.addPlayer(secondPlayer);
----

The `Team` stores references to its players, but it does not create or control their lifetime.

This is modeled as an aggregation.

Aggregation is therefore a specific kind of has-a relationship: the whole contains or groups parts, but the parts can conceptually exist independently.

Simplified UML:

[source,text]
----
Team ◇──────── Player
----

The hollow diamond is placed at the `Team` side because `Team` represents the whole.

The relationship is unidirectional in this example:

* `Team` knows its `Player` objects;
* `Player` does not store a reference back to `Team`.

`List<Player>` is used only to store multiple player references. Collections are not the topic of this chapter.

== Association

Association is the broadest relationship term in this chapter.
If one object stores or uses another object, the model can describe that as an association.
Aggregation and composition add more specific whole-part meaning.

Simplified UML:

[source,text]
----
    ClassA
     |
     |
     |
    ClassB
----

== Direction

The examples are unidirectional:

* `Car` knows its `Engine`;
* `Engine` does not store a reference back to `Car`;
* `Team` knows its `Player` objects;
* `Player` does not store a reference back to `Team`.

Bidirectional relationships are possible and are explained in xref:DEEP_DIVE.adoc#or-bidirectional[the deep dive].

== Multiplicity

Multiplicity describes how many objects may participate at one end of a relationship.

For the `Team` example, one team may contain any number of players:

[source,text]
----
Team 1 ◇──────── 0..* Player
----

Common UML multiplicities include:

* `1..1` - exactly one;
* `0..1` - zero or one;
* `0..*` - any number including zero;
* `1..*` - one or more.

== Summary

Java code stores references between objects; the model gives those references meaning. Association is general, while aggregation and composition add whole-part semantics.
